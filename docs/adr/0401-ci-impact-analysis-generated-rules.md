# ADR 0401 — Impact analysis via generated `rules:changes` (no Nx/Turbo, no child pipelines)

- Status: Accepted

## Context

The monorepo has ~20 workspace packages. Running every job on every MR wastes a
small runner fleet (often one generic runner), but skipping a job that a change actually
affects is unacceptable. GitLab evaluates `rules` when a pipeline is created, so a
job's output (e.g. a dotenv) cannot remove later jobs. Nx/Turbo were out of scope.

Options considered:

1. **Dynamic child pipeline** (`trigger: include: artifact`, `strategy: depend`)
   generated by an analysis job. Precise at runtime, but JUnit/coverage/Code
   Quality/SBOM reports of child pipelines are not aggregated into the MR widget,
   the gate and the visible DAG split across two pipelines, and debugging gets harder.
2. **Generated, checked-in `rules:changes`** per component, including the paths of
   every transitive workspace dependency and the global paths, plus a runtime
   analyser that cross-checks.
3. Hand-written `rules:changes` — drifts from the dependency graph immediately.

## Decision

Option 2. `tools/impact` reads `pnpm-workspace.yaml`, every `package.json`
(`workspace:` edges) and `components.yaml` (`dependsOn` for edges that are not
package dependencies, e.g. CDK bundling Lambda sources), and generates
`.gitlab/ci/generated/components.yml`:

- `.impact:<component>` rules: never in task-only schedules; always on the default
  branch, tags, schedules, web/API triggers and `IMPACT_RUN_ALL=true`; otherwise
  `changes:paths` = own paths ∪ transitive dependencies' paths ∪ global paths.
- generated jobs: `test:<component>`, the container chain for container components,
  synth (matrix)/policy/FinOps for infra, `integration:<component>`, and
  `gates:mandatory` with `needs` on every gated job.

Safety nets:

- The `impact` job regenerates in memory and **fails if the checked-in file is stale**;
  lefthook regenerates on commit.
- Changed paths not mapped by `components.yaml` (component path, `extraPaths`,
  `global`, `nonComponent`) **fail** the `impact` job.
- Missing/zero base SHA or git errors → run-all; the gate then requires every job
  (and tells you to re-run with `IMPACT_RUN_ALL=true` if GitLab's own selection was
  narrower).
- `gates:mandatory` compares the runtime analysis with success markers of the jobs
  that actually ran.
- The glob matcher reimplements GitLab's Ruby `fnmatch` flags; a unit test simulates
  GitLab's rule evaluation and asserts it selects exactly what the analyser selects.

## Consequences

- MR widget shows all reports; the DAG is one pipeline.
- Adding a component = workspace package + one `components.yaml` entry + regenerate.
- `rules:changes` allows ≤ 50 patterns; the generator fails beyond that (consolidate
  with brace patterns). `needs` is limited to 50 entries per job by default; the gate
  currently needs ~35 — beyond that, raise `ci_needs_size_limit` or aggregate.
- The generated file must be regenerated after dependency changes (enforced).
